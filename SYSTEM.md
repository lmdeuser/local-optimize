# Local Optimize — описание системы

## Эксплуатация поиска: актуальный контракт 2026-11-01

Подсистема выдаёт агентам найденные свидетельства с источником, статусом проверки
и актуальностью файла. Оценка релевантности не доказывает истинность текста.
При недостатке свидетельств ответ пустой с `insufficient_evidence`; вызывающий
агент должен продолжить исследование. Чужие приватные сессии не входят в shared scope.
Эмбеддинги и оценка релевантности выполняются на Intel XPU, без CUDA и CPU fallback.
Процессор обслуживает HTTP, токенизацию, файловую систему и PostgreSQL.

Пароли подключения к базе хранятся в защищённом файле
`~/.config/local-optimize/secrets.env`; `config.py` загружает параметры через
`load_secrets_file`, представляет значения обёрткой `SecretString` и маскирует
их при выводе. Этот путь описывает механизм хранения, а не значение пароля.
Секретный файл расположен вне индексируемого проекта и не является источником RAG.

При занятых четырёх поисковых слотах HTTP возвращает 503 `RAG_SEARCH_BUSY`
(`Search workers are occupied`). Истечение срока ожидания не освобождает слот,
пока работа действительно не завершилась. Это ограничивает очередь запросов.

## Назначение

**Local Optimize** — это локально-ориентированная система долговременной когнитивной памяти и гибридного инференса (Local-First Hybrid Inference & Cognitive Memory Architecture) для AI-агентов и сред разработки (Cursor, Google Antigravity, Gemini CLI, OpenCode, VSCode, Claude Desktop и автономных субагентов). Система создана для устранения проблемы «амнезии» LLM-сессий, когда агенты вынуждены повторно исследовать проект, заново выводить архитектурные решения и терять контекст между перезапусками.

Система консолидирует кодовую базу, архитектурную документацию, граф сущностей и связей (GraphRAG), операционные правила и инженерные навыки (skills) в централизованном хранилище на базе PostgreSQL с расширением pgvector. Все операции чтения и записи строго разграничены по контекстам проектов, областям видимости и владельцам (Agent ID / Session ID), предотвращая утечки данных между сессиями и проектами.

В основе инференса лежит двухуровневая архитектура (локальная двухслойка) с каскадной эскалацией запросов по уровню уверенности:
- **Слой 1 (Локальный)**: RAG + модель из `local_model.json` (`qwen2.5-coder:7b`, контекст 8192). Модель загружается при первом запросе и запрашивается с `keep_alive: -1`; общая реализация `local_inference.py` разрешает генерацию только когда `/api/ps` сообщает полное размещение (`size_vram >= size`) и ожидаемый контекст. При неизвестном или неполном размещении запрос завершается без генерации и без CPU-fallback. Метрика Ollama — проверка по телеметрии, а не независимое измерение физической VRAM. При достаточных источниках запрос может быть закрыт локально без облачной генерации.
- **Граница облачной эскалации**: Облачный backend получает только исходный запрос пользователя в отдельном вызове без истории локального чата. Фрагменты и ответы RAG, цитаты, оценки, метаданные источников, сводки и производные факты запрещены в облачном payload. Если клиент не умеет отделить исходный запрос от истории/результатов MCP или облачному агенту доступны инструменты RAG, эскалация блокируется.
- Claude Code хуки не внедряют RAG в облачную сессию; RAG MCP нельзя подключать к облачным агентам напрямую. Для них допустим только отдельный handoff с исходным запросом пользователя и без доступа к инструментам/истории RAG.

## Путь запроса

Сквозной путь прохождения запроса в производственной среде:

1. **Инициация вызова (MCP Client / Agent IDE)**:
   Агент (Cursor, Antigravity, Gemini и др.) вызывает один из зарегистрированных инструментов MCP (например, `rag_search` или `route_query_tool`) через `stdio` или HTTP JSON-RPC.
2. **Обработка в MCP-сервере (`mcp_server.py`)**:
   Сервер распаковывает аргументы, формирует объект корреляции (`correlation_id`, `agent_id`, `session_id`) и конструирует `ProjectContext` с указанием `project_id`, `root_id`, `write_visibility` и `read_scope`. Для сетевого взаимодействия вызывается экземпляр `RagClient`.
3. **HTTP-клиент (`rag_client.py`)**:
   `RagClient` сериализует запрос в JSON, проверяет размер тела запроса (`MAX_REQUEST_BODY_BYTES`), проставляет заголовки `X-Local-RAG-Session` и `Authorization: Bearer <token>`, после чего выполняет POST-запрос к FastAPI серверу (`gpu_rag_server.py`).
4. **FastAPI Шлюз (`gpu_rag_server.py`)**:
   - Middleware `limit_body_size` проверяет объем входящих данных.
   - Эндпоинт (например, `/search`) валидирует Pydantic-схему `SearchRequest`.
   - Реестр `ProjectRegistry` валидирует `ProjectContext` по контрольной сумме (`registry_fingerprint`) и подтверждает канонические пути корней.
5. **Выполнение в RAG-движке (`rag_engine.py`)**:
   - **Токенизация и векторизация**: Текст запроса преобразуется в вектор размерности 384 через локальную модель (`multilingual-e5-small`).
   - **Генерация SQL с изоляцией ACL**: Модули `build_read_scope_sql` и `build_evidence_acl_sql` формируют предикаты безопасности (`visibility`, `agent_id`, `session_id`, `is_active = TRUE`, исключение `deprecated`/`invalidated`).
   - **Гибридная выборка из PostgreSQL**: Векторный поиск по косинусному расстоянию (`embedding <=> query_vec`) и полнотекстовый поиск по `fts_tokens` через `websearch_to_tsquery` формируют независимые пулы кандидатов.
   - **Локальная векторизация**: `SentenceTransformer` загружает модель внутри RAG-процесса на Intel Arc через `torch.xpu`; CPU fallback отсутствует; при недоступном XPU инициализация завершается ошибкой.
   - **Сведение рангов кандидатов (`compose_final_scores`)**: Оценки семантики, RRF, лексического буста, давности (`recency_decay`) и авторитетности (`authority_weight`) объединяются в `candidate_score` на шкале [0.0, 1.0]. Этот score упорядочивает recall, но не является финальным решением о выдаче.
   - **Финальный evidence reranking**: Локальный `Qwen3-Reranker-0.6B` на Intel XPU оценивает кандидатов против исходного вопроса и дополнительного смыслового аспекта. После versioned policy threshold итоговый `final_score` заменяет candidate score; при сбое возвращается `unavailable`, без CPU fallback.
   - **GraphRAG (при вызове `/agentic-search`)**: Выполняется BFS-обход графа сущностей `kb_entities` и связей `kb_relations` с фильтрацией через `entity_evidence` и `relation_evidence`.
6. **Маршрутизация и двухуровневый инференс (`fast_router.py`)**:
   При вызове `route_query_tool` движок `AdaptiveModelRouter` сопоставляет RAG-метрики с настроенным порогом `relevance_floor` (0.50 по умолчанию) и анализирует сложность запроса:
   - **Слой 1 (Локальный)**: Если контекст RAG проходит проверку достаточности и задача подходит локальной генерации, запрос передается модели и с контекстом из `local_model.json` через `local_inference.py`. Перед и после генерации проверяются модель, контекст и полное GPU-размещение по `/api/ps`; при неподтвержденном размещении генерация не выполняется. Локальная модель не предзагружается при старте процесса. Ответ может возвращаться как `route: "respond"`, `layer: "layer_1_local"` с текстом в `response`; формат зависит от вызывающего MCP-инструмента.
   - **Расширение доступной памяти**: Ollama получает окно `num_ctx=8192` по умолчанию (`OLLAMA_NUM_CTX`), а RAG передает до пяти найденных фрагментов с provenance в пределах 3500 символов (`RAG_EVIDENCE_MAX_CHARS`). База работает как внешняя поисковая память: она подбирает материалы для каждого запроса, но не увеличивает постоянное нативное окно модели. Оба лимита настраиваются переменными окружения.
   - **Слой 2 (Изолированная облачная эскалация)**: При нехватке данных или высокой сложности возвращается только сигнал `route: "escalate"`. Фрагменты RAG, цитаты, метаданные источников, оценки, сводки и любые производные от RAG в облако не передаются. Облачный адаптер может получить только исходный запрос пользователя, отдельно от истории локального чата; если изоляция не обеспечена, эскалация блокируется. Cloud-capable клиенты, включая Kimi Code с облачной моделью, не подключают RAG MCP напрямую.
   - **Проверка источников**: Для структурированных результатов обычному запросу нужен минимум один из пяти фрагментов, сложному — минимум два и хотя бы один источник `validated` или `authoritative`. Локальный ответ должен ссылаться на существующие `[Evidence N]`; иначе запрос эскалируется. MCP возвращает `response_sources` с provenance процитированных фрагментов.
7. **Формирование и проверка ответа**:
   `gpu_rag_server.py` возвращает статус `success`, `error` или `unavailable`. `RagClient` выполняет строгую валидацию структуры ответа и передает результат в MCP-сервер, который отдает форматированный JSON в интерфейс агента.

## Хранилище данных

Хранилище развернуто в базе данных PostgreSQL `aiagent`, все объекты размещены в схеме `public`. Для векторных операций подключено расширение `pgvector`.

### Основные таблицы и ключевые поля

- `schema_migrations`: Реестр миграций (`version` PK, `filename`, `checksum` SHA-256, `execution_status`, `applied_at`, `reconciled_at`, `reconciliation_method`).
- `project_knowledge`: Канонические текстовые чанки и их векторные представления.
  - `id` (BIGSERIAL PK), `project_id`, `root_id`, `file_path`, `content`, `content_hash` (SHA-256).
  - `dedup_key` (TEXT UNIQUE) — уникальный дедупликационный ключ.
  - `embedding` (`vector(384)`) — вектор эмбеддинга.
  - `fts_doc_tokens` (`tsvector`) — токены для полнотекстового поиска (русский + английский словари).
  - `visibility` (`public`, `shared`, `agent-private`, `session-private`).
  - `agent_id`, `session_id` — идентификаторы владельцев.
  - `validation_status` (`unverified`, `validated`, `authoritative`, `deprecated`, `invalidated`).
  - `importance` (INT, 1–5), `verified_at` (TIMESTAMPTZ), `recheck_after_days` (INT), `entity_id` (BIGINT FK к `kb_entities`).
- `kb_documents`: Учет индексируемых документов и файлов (`id` PK, `project_id`, `root_id`, `file_path`, `source_type`, `content_hash`, `is_active`, `created_at`, `updated_at`).
- `knowledge_provenance`: Связь многие-ко-многим между чанками и исходными документами (`id` PK, `project_id`, `root_id`, `chunk_id` FK, `document_id` FK, `source_uri`, `start_locator`, `end_locator`). Сохраняет ссылки на все источники при совпадении контента.
- `kb_entities`: Канонические сущности семантического графа (`id` BIGSERIAL PK, `project_id`, `name`, `stable_key` UNIQUE, `entity_type`, `description`, `metadata`).
- `kb_relations`: Канонические направленные ребра графа (`id` BIGSERIAL PK, `project_id`, `from_entity_id` FK, `to_entity_id` FK, `relation_type`, `weight`, `metadata`).
- `entity_evidence`, `relation_evidence`: Слой изоляции доступа (Evidence ACL) для графа. Связывает канонические сущности и связи с конкретными `project_id`, `root_id`, `visibility`, `agent_id`, `session_id`, `validation_status`, `document_id` и `chunk_id`.
- `kb_feedback_logs`: Логирование пользовательской и агентской обратной связи (`query`, `feedback_type`, `correction`, скоринг).
- `agent_sessions`, `agent_messages`: Операционные очереди и журнал межсессионных сообщений (с поддержкой выборки через `FOR UPDATE SKIP LOCKED`).

### Дедупликация и обновление

- Дедупликационный ключ `dedup_key` формируется как SHA-256 хеш от кортежа:
  `project_id | content_hash | visibility | owner_agent | owner_session`
  *(Примечание: начиная с миграции v10, `validation_status` исключен из `dedup_key`, что позволяет атомарно обновлять статус существующего чанка без дублирования строк).*
- Запись выполняется через конструкцию `INSERT ... ON CONFLICT (dedup_key) DO UPDATE`.
- При повторном сохранении идентичного контента из нового файла создается новая запись в `knowledge_provenance`, сохраняя историю всех источников.
- Чанки со статусом `deprecated` или `invalidated` защищены от случайного автоматического перетирания рутинными операциями сохранения (`save`).

## Поиск и ранжирование

Система реализует гибридный многофакторный пайплайн ранжирования:

### 1. Конфигурация модели эмбеддингов
В коде сконфигурирована модель **`multilingual-e5-small`** (`EMBEDDING_MODEL_NAME = "multilingual-e5-small"`, версия `EMBEDDING_VERSION = "2.0"`, размерность `EMBEDDING_DIM = 384`).
Модель выбрана по результатам эмпирического тестирования корпуса (документ `docs/embedding-model-evaluation.md`), где она превзошла англоязычную `all-MiniLM-L6-v2` и `paraphrase-multilingual-MiniLM-L12-v2`, показав трехкратный прирост Recall@1 на русскоязычных парафразах (0.259 против 0.086).

### 2. Выборка кандидатов
- **Векторный поиск**: Выборка ближайших строк по косинусному расстоянию pgvector (`embedding <=> query_vec`).
- **Полнотекстовый поиск (FTS)**: Выборка по полнотекстовому индексу PostgreSQL с вычислением `ts_rank_cd`.
- **RRF (Reciprocal Rank Fusion)**: Первичное слияние позиций кандидатов:
  `rrf = (w_vec / (k + rank_vec)) + (w_fts / (k + rank_fts))`, где `k = 60`, `w_vec = 1.0`, `w_fts = 0.5`.

### 3. Ранжирование кандидатов на фиксированной шкале
Для сопоставимости candidate scores между запросами `compose_final_scores` приводит косинус к шкале [0.0, 1.0] через опорные точки активного профиля модели и объединяет его с RRF:
- `semantic = clip((cosine - cos_lo) / (cos_hi - cos_lo), 0.0, 1.0)`
- `rrf_scaled = clip(rrf / RRF_REFERENCE, 0.0, 1.0)`, где `RRF_REFERENCE = (w_vec + w_fts) / (k + 1)`
- `base = SCORE_ALPHA * semantic + (1.0 - SCORE_ALPHA) * rrf_scaled` (при `SCORE_ALPHA = 0.7`)

На candidate score также влияют:
- **Recency Decay**: экспоненциальное затухание по времени последней верификации/создания (`verified_at` или `created_at`).
- **Authority Weight**: вес по статусу валидации (`unverified` = 0.95, `validated` = 1.1, `authoritative` = 1.2); `deprecated` и `invalidated` отфильтровываются в SQL.
- **Lexical Boost**: добавка за словарные совпадения ключевых терминов.
- **Формула кандидата**: `candidate_score = clip(base * recency_decay * authority_weight + lexical_boost, 0.0, 1.0)`.

### 4. Финальный evidence reranking
Кандидаты проверяются локальным `Qwen3-Reranker-0.6B` против исходного вопроса, а не расширенного варианта. В `retrieval_policy.json` зафиксированы модель и revision, лимит 24 основных и до 8 дополнительных document-кандидатов, 768 токенов на пару, batch 4 и deadline 15 секунд. Дополнительная facet-проверка отсекает совпадения только по имени сущности. Итоговый `final_score` — это relevance score Qwen, сохранённый candidate score доступен отдельно как `candidate_score`. Оценка релевантности не доказывает истинность утверждения.

### 5. Порог релевантности
Общий порог зафиксирован в `config.py` как **`relevance_floor = 0.50`** по умолчанию. Эффективный порог evidence ranker — максимум из `retrieval_policy.relevance_threshold` и `context.min_score`. Эндпоинт `/search` дополнительно применяет максимум из `context.min_score` и общего `RAG_CONFIDENCE_THRESHOLD`, повторно отфильтровывая нижепороговые результаты, включая старые кешированные ответы. Роутер может повысить порог для сложного запроса.

### 6. Кеширование результатов

Поиск обслуживают три яруса, от дешёвого к дорогому: процессный кеш, общий кеш в PostgreSQL и собственно гибридный поиск с evidence reranking.

- **L1 (`query_cache.BoundedTTLCache`)** — ограниченный TTL/LRU в памяти воркера. Значения копируются на входе и выходе, параллельные промахи по одному ключу схлопываются в одно вычисление.
- **L2 (`query_cache.PersistentQueryCache`, миграция 0013)** — таблица `rag_query_cache`, общая для процессов и переживающая перезапуск. Реализация поддерживает exact и semantic lookup, но production `RagEngine` фиксирует semantic threshold на 1.0: переиспользуется только тот же нормализованный вопрос по `(scope_hash, query_hash)`.
- **Ключ области (`RagEngine._search_scope_key`)** — включает идентичность **только там, где её читает `build_read_scope_sql`**: при `public` и `shared` ни агент, ни сессия в SQL не связываются. `RagEngine.SEARCH_SCOPE_FIELDS` фиксирует набор полей `ProjectContext`, от которых вправе зависеть SQL поиска; тест `test_search_scope_key.py` выводит этот набор из исходника и падает при расширении фильтра без правки ключа.
- **Инвалидация** — счётчик поколений `rag_cache_generation`, по одному на проект. Бумпается на **изменение корпуса или evidence**, а не на каждую запись: индексация объединяет новые и superseded chunks в один бумп на логическое изменение файла. Конфликт по `dedup_key` сам по себе не инвалидирует кеш, но изменение `validation_status` или `source_snapshot` может это сделать. Каждый воркер держит копию счётчика `RAG_CACHE_GENERATION_REFRESH_SECONDS` (5 с) — это окно устаревания общего кеша.
- Ответ из кеша несёт блок `cache` с указанием яруса. Семантический вопрос и близость были бы видны при near-miss, но в текущем production exact-only режиме такие попадания отключены.
- **Соединение одалживается, а не берётся заново.** Инвалидация — последнее действие записи, и она происходит, пока писатель ещё держит соединение из пула. Запрос второго превращал писателя в конкурента самому себе: при `maxconn=16` шестнадцать одновременных писателей исчерпывали пул, бумп падал, отказ был не виден (путь отказывает открыто) — запись коммитилась, счётчик не двигался, остальные процессы продолжали отдавать то, что она должна была погасить. Найдено по симптому на живом сервере (12 замороженных ошибок) и воспроизведено точно: `PoolError: connection pool exhausted`, `generation_bumps` = 0 при `save()` = success. Сторож `tests/unit/test_cache_connection_reuse.py` обходит AST движка и падает на любом новом писателе, добавленном по старому образцу.
- **Нечитаемый счётчик — не то же самое, что неизменившийся.** Если `generation()` вернул `None`, воркер не знает, инвалидировал ли что-то сосед. Для такого запроса обходятся **оба** яруса — и L1, и L2 — на чтение и запись; ответ помечается `{"layer": "unshared"}`, а не промахом.
- Любая операция L2 отказывает открыто: недоступный кеш выглядит ровно как холодный.

Эксплуатация: `GET /cache/stats`, `POST /cache/invalidate`. Подробности — `docs/query-cache.md`.

### 7. Компактный формат ответа

`response_format.py` задаёт три отрисовки одного и того же ответа: `full` (всё, для аудита), `compact` (по умолчанию для агентских инструментов) и `minimal` (только адреса и скоры, без текста). Компактная форма выбрасывает диагностику — покомпонентные скоры, хеши, провенанс модели у каждого хита — и опускает поля, совпадающие со значением по умолчанию. Замер на реальном ответе из пяти хитов: **10139 → 5103 байт (−50%)**, `minimal` — 436 байт (−96%). Раскрытие происхождения из кеша компактная форма сохраняет всегда.

## Модель безопасности

Безопасность системы построена на строгой изоляции файловой системы и разделении прав доступа к данным в СУБД:

### Границы файловой системы (`ProjectRegistry` и `validate_path`)
- Сервер является единственным источником правды о зарегистрированных проектах (`projects.json` / `PROJECTS_REGISTRY_FILE`) и их корнях (`roots`).
- Клиент передает только идентификаторы `project_id` и `root_id`. Клиентские подсказки путей могут только сужать область поиска, но не расширять ее.
- `validate_path()` нормализует пути, блокирует `..`, запрещает выход за пределы активного `project_root` через симлинки и исключает доступ к соседним корням (sibling roots).

### Области видимости записи (`WriteVisibility`)
- `public`: Доступно для чтения всем агентам во всех сессиях.
- `shared`: Общедоступно в рамках проекта для всех агентов.
- `agent-private`: Доступно только агенту с совпадающим `agent_id`.
- `session-private`: Доступно строго в рамках комбинации `agent_id` + `session_id`.

### Области видимости чтения (`ReadScope`)
- `public`: Возвращает только записи с `visibility = 'public'`.
- `shared`: Возвращает записи с `visibility IN ('shared', 'public')`.
- `agent`: Возвращает `shared`, `public`, а также `agent-private` (при точном совпадении `agent_id`). Если `agent_id` не передан, предикат схлопывается в `1=0` (безопасный пустой результат).
- `session`: Возвращает `shared`, `public`, `agent-private`, а также `session-private` (при совпадении `agent_id` и `session_id`). При отсутствии идентификаторов предикат возвращает `1=0`.

### Статус валидации (`ValidationStatus`)
Статусы `unverified`, `validated`, `authoritative`, `deprecated`, `invalidated` отражают качество и жизненный цикл знаний и **никогда** не подменяют собой права доступа.

## Хуки редактора

Вызов инструмента стоит выходных токенов на его формирование и происходит только тогда, когда модель уже подозревает, что память существует. Хук срабатывает раньше, ничего не стоит модели и отдаёт результат промптом — дешёвым видом токенов. На этой асимметрии построены три скрипта в `hooks/` (только стандартная библиотека, старт ~30 мс):

| Событие | Скрипт | Действие |
| :--- | :--- | :--- |
| `UserPromptSubmit` | `rag_user_prompt.py` | Отключен: не делает RAG-запрос и не вкладывает память в облачный диалог. |
| `SessionStart` | `rag_session_start.py` | Отключен: не делает RAG-запрос и не вкладывает память в облачную сессию. |
| `Stop` | `rag_harvest.py` | Извлекает долговременные факты из транскрипта в очередь на ревью. **Выключен по умолчанию.** |

`POST /hook/context` строит `ProjectContext` на стороне сервера для разрешённого local-only сценария. Отключённые prompt/session hooks этот endpoint не вызывают. Любой сбой — таймаут, отказ соединения, некорректный JSON — заканчивается одинаково: ничего не вкладывается, выход 0.

Для разрешённой локальной инъекции предусмотрены порог релевантности 0.50 и дельта по `injected_hashes`, чтобы не передавать один и тот же абзац на каждом ходу. Текущие облачные hooks инъекцию не выполняют. Установка — `hooks/install.py`, подробности — `docs/hooks.md`.

## Скиллы

Система управления навыками обеспечивает стандартизированными инструкциями все подключенные AI-агенты:

- **Каталог `skills/`**: Единый источник правды (Single Source of Truth), содержащий 39 канонических `.md` файлов и `manifest.json`. Манифест строго описывает идентификаторы, версии, SHA-256 контрольные суммы, обязательные скиллы (`required`) и ключевые слова активации (`activation_keywords`).
- **Каталог `refactored-agent-skills/`**: Модульный репозиторий с эталонными версиями скиллов, используемый для версионирования и экспорта.
- **Диспетчер `skills_manager.py`**:
  - `load_manifest(strict=True)` валидирует структуру, глубину вложенности JSON и контрольные суммы файлов.
  - `SessionSkillsManager` реализует изолированный LRU-кэш для каждой пары `(agent_id, session_id)` с TTL 1 час (`SESSION_TTL_SECONDS = 3600`).
  - Лимиты безопасности: максимум 10 скиллов на сессию (`MAX_SKILLS_PER_SESSION = 10`), не более 256 КБ на один файл (`MAX_SKILL_BYTES = 262144`), суммарно до 1 МБ на сессию (`MAX_SESSION_BYTES = 1048576`).
  - `sync_to_targets(clean_stale=True)` синхронизирует канонические скиллы в 4 целевые директории сред разработки (`~/.gemini/antigravity/skills`, `~/.gemini/skills`, `~/.gemini/antigravity-cli/skills`, `~/.cursor/skills`). Ownership-state `.local-optimize-sync.json` позволяет удалять только ранее синхронизированные файлы с совпадающим SHA-256; пользовательские и изменённые файлы сохраняются.

## Миграции

Управление схемой базы данных полностью изолировано внутри `migration_runner.py`:

- **Принцип работы**: Файлы миграций расположены в `migrations/0001_baseline.sql` — `0014_local_answer_cache.sql` и зарегистрированы в `migrations/manifest.json`. Движок `RagEngine` работает строго в режиме read-only и никогда не применяет DDL на лету. Обязательная v13 добавляет query cache и generation counters; необязательная v14 добавляет validated local answer cache.
- **Блокировки и транзакционность**: Перед анализом и выполнением миграций берется стабильный сессионный PostgreSQL advisory lock с ограниченным таймаутом. Каждая миграция и запись в таблице `schema_migrations` фиксируются в одной транзакции (`commit`).
- **Обработка сбоев (Committed Boundary)**: При ошибке транзакция текущей миграции откатывается (`rollback`), а ранее зафиксированные версии объявляются неизменной границей. Деструктивные откаты в БД автоматически не выполняются.
- **Сверка легаси-схем (`reconcile_legacy`)**: Если таблица существовала до появления манифеста контрольных сумм, строка получает статус `legacy-unverified`. Метод выполняет проверку всех инвариантов (таблицы, колонки, индексы, внешние ключи) и только при полном совпадении проставляет SHA-256.
- **Проверка во время работы (`verify_runtime_schema`)**: При старте сервера проверяется наличие всех обязательных миграций, валидность их хешей и фактическое присутствие объявленных инвариантов схемы в `information_schema` и `pg_indexes`.

Для применения миграций используется команда:
```bash
python3 migration_runner.py
# или через центральный инициализатор:
python3 create_schema.py
```

### Индексация кодовой базы
- **Автоматическая индексация (`watchdog_indexer.py`)**: Работает как фоновый сервис systemd (`local-optimize-watchdog.service`). Отслеживает изменения файлов в `project_root`, фильтрует бинарные файлы и кэши (`.venv`, `__pycache__`, `node_modules`), дебаунсит события (1.0 сек) и отправляет запросы на `/index_code`, `/index_document`, `/delete_document` или `/move_document` на центральный RAG-сервер. При перемещении файлов переименование выполняется в одной транзакции на стороне БД.
- **Пакетная ручная индексация (`index_project_codebase.py`)**: Выполняет полный рекурсивный обход директории проекта и пакетную загрузку кода (`.py`) и документации (`.md`, `.sql`, `.sh`, `.json`) с областью видимости `shared`.

### Перерасчет эмбеддингов (`reembed_corpus.py`)
При смене модели эмбеддингов в конфигурации прямое сравнение векторов становится невозможным. Скрипт `reembed_corpus.py`:
- Проверяет количество строк, требующих обновления (`embedding_model IS DISTINCT FROM ...`).
- Пересчитывает векторы пачками (`execute_batch`) без изменения текстового контента.
- Поддерживает безопасный перезапуск с места остановки (resumable) и режим предварительного просмотра (`--dry-run`).

### Резервное копирование (`postgres_backup.sh`)
- Защищен от параллельного запуска файловой блокировкой `flock` (`/var/run/postgres-backup.lock`).
- Создает бинарные дампы `pg_dump -Fc` через временные файлы с валидацией целостности командой `pg_restore --list`.
- Хранит резервные копии с глубиной ротации 7 дней (`RETENTION_DAYS=7`).

### Бенчмаркинг качества RAG (`rag_benchmark.py`)
- Запускает валидацию по эталонному датасету `GOLD_DATASET`.
- Проверяет точность выборки терминов для архитектурных, SQL, русскоязычных и англоязычных запросов, а также корректность отрицательного ответа для отсутствующих тем.

## Известные ограничения

Здесь отделены действующие ограничения от исторических замеров (`PROJECT_AUDIT.md`, `AUDIT_BRIEF.md` и `docs/score-calibration.md`); старые числа не являются текущими serving thresholds.

1. **Косинусный reranker остаётся только этапом candidate scoring**:
   - `XpuReranker` считает косинус между теми же векторами, которые участвовали в отборе, поэтому не добавляет новой информации; его результат используется для recall и candidate score, а не как финальное evidence-решение.
   - Текущий финальный `EvidenceRanker` использует `Qwen3-Reranker-0.6B` на Intel XPU и оценивает исходный вопрос вместе с фрагментом. Его отказ возвращает `unavailable`, без возврата к косинусной выдаче.
   - Исторический замер 2026-08-21 отклонил `bge-reranker-base` и `bge-reranker-v2-m3`: на инженерном вопросе они давали 0.0010 и 0.0035 из-за несовпадения распределения MS MARCO с проектной документацией. Это результат о старых BGE-кандидатах, а не о текущем Qwen. Инструмент проверки сохранён — `probes/rerank_paraphrase_probe.py`.

2. **Историческое ограничение E5 на длинных русских запросах**:
   - Замер candidate pipeline: запрос «как устроено кеширование запросов и инвалидация по поколениям» дал сырой косинус 0.8539 — ниже уровня шума `multilingual-e5-small` (p95 = 0.8639), candidate score 0.19 при тогдашнем пороге 0.30. Короткий вариант дал 0.74.
   - Это измерение относится к отбору кандидатов и старой шкале, а не к текущему Qwen threshold 0.50. Оно мотивирует проверку recall на парафразах, но не является свежей оценкой качества всего двухступенчатого поиска.

3. **Измеренные и отклонённые оптимизации выдачи (2026-08-21)** — записаны, чтобы их не предлагали заново:
   - *Прогрев кеша по журналу запросов* — не окупается. Холодный поиск ~200 мс, тёплый L1 — 0.1 мс, L2 — ~20 мс; экономия разовая на каждый различный запрос. Замер `rag_query_cache`: 19 строк, 14 попаданий, переиспользовано 7 строк, максимум 5. Переиспользование реально, но лидер — детерминированный запрос хука `SessionStart`, а не хвост, который стоило бы прогревать.
   - *Дедупликация перекрывающихся чанков в ответе* — не окупается. Смежные чанки действительно попадают в одну выдачу (6 пар на 50 хитов по 10 реальным запросам), но продублированного текста 808 символов из 48516 — **1.7%**.
   - *Что при этом вскрылось и перспективнее обоих* — качество нарезки, а не формата: отдельные чанки почти целиком содержатся в соседе (`SYSTEM.md#32,#33` — 128 общих символов из 129; `#9,#10` — 198 из 227). Такой чанк занимает слот выдачи, не добавляя ничего. Правка требует переиндексации корпуса.

4. **Неактивный функционал в `rag_engine.py`**:
   - Метод `execute_and_learn()` отключен по умолчанию и требует явного флага `ENABLE_EXECUTE_AND_LEARN=1`.
   - Внутренний метод `auto_index_codebase()` в `rag_engine.py` не запускает отдельный поток; вся автоиндексация полностью делегирована сервису `watchdog_indexer.py`.
   - Переменная `AUTO_INDEX_ENABLED` объявлена в `rag_engine.py`, но не считывается логикой движка.
   - Вспомогательная функция `_index_document_without_chunking()` не имеет активных потребителей.
5. **Безопасный режим оптимизации памяти**:
   - Функция `memory_optimize()` работает в режиме `safe-no-delete` (`deleted` всегда 0): она находит и возвращает список семантических дубликатов, но не удаляет их автоматически во избежание потери контекста.
6. **Особенности интеграции с OpenCode**:
   - В версиях OpenCode конфигурация MCP считывается из `~/.config/opencode/opencode.json` под ключом `"mcp"`. Генератор `mcp_config_generator.py` формирует файл `mcp.json` для обратной совместимости, поэтому для работы в OpenCode требуется ручное слияние секции `local-rag`.
7. **Зависимости в `requirements.txt`**:
   - В зависимостях присутствуют библиотеки `transformers` и `sentence-transformers`, в то время как основной путь загрузки модели использует оптимизированную загрузку через SentenceTransformer на Intel XPU.
8. **Языковая специфика промптов роутера**:
   - `FORMATTER_SYSTEM_PROMPT` в `fast_router.py` содержит русскоязычные инструкции форматирования, в то время как системные контракты остальных компонентов спроектированы на английском языке.
