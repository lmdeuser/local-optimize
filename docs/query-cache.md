# RAG query cache

Three tiers answer a search, cheapest first.

## L1 — process-local (`query_cache.BoundedTTLCache`)

Bounded TTL/LRU, per worker. Absorbs bursts: the same question asked twice in
one turn is computed once. Results are deep-copied in and out so callers cannot
mutate cached state, and concurrent misses for one key are coalesced into a
single computation. A separate embedding cache stores query and passage vectors;
it is keyed by content and model, so nothing invalidates it but time.

## L2 — shared, in Postgres (`query_cache.PersistentQueryCache`, migration 0013)

L1 dies with the process and is invisible to every other process. L2 is the same
answers in `rag_query_cache`, so a restart is not amnesia and an answer computed
by the MCP server also serves the CLI, the indexer and tomorrow's session.

The reusable implementation supports two lookups, in order:

- **exact** — `(scope_hash, query_hash)`;
- **near-miss** — nearest `query_embedding` neighbour above
  `RAG_L2_CACHE_SEMANTIC_THRESHOLD`. The historical 0.98 setting inherits
  `DUPLICATE_SIM_THRESHOLD`'s calibration: on `multilingual-e5-small` unrelated
  text already sits at 0.86, so lower values risk treating noise as a paraphrase.

Production `RagEngine` pins the semantic threshold to **1.0**. Consequently,
current serving reuses an evidence decision only for the same normalized
question; the near-miss mechanism is disabled even though the cache implementation
retains it. Re-derive any future lower threshold against the active embedding
model and evidence policy before enabling it.

A response served from cache carries a `cache` block naming the tier. If semantic
reuse is ever enabled, a near-miss hit also reports the question it actually
matched and how closely, so one question's answer is never silently presented as
another's.

## Validated local answer cache

`rag_local_answer_cache` is a separate exact-match cache for the final text
generated by the local Ollama model. The cache key hashes the fully rendered
question and evidence, formatter system prompt, model name, generation options,
privacy mode, and `LOCAL_ANSWER_CACHE_VERSION`. It stores the answer text and
hashes, not a second copy of the prompt or retrieved documents. Semantic answer
reuse is deliberately disabled.

Only a model answer that passes the existing evidence-citation checks is stored.
Insufficient-data responses, policy fallbacks, invalid citations, and cloud
escalations are never cached. The key is scoped to the authorized project and
read scope. Knowledge writes retire answers through the same per-project
generation counter used by the search cache; storage also checks that generation
again after inference to avoid filing a stale answer under a newer generation.

Defaults are a 900-second TTL and 5,000 rows, configurable with
`RAG_LOCAL_ANSWER_CACHE_TTL_SECONDS` and
`RAG_LOCAL_ANSWER_CACHE_MAX_ROWS`. `LOCAL_ANSWER_CACHE_VERSION` can be incremented
to retire answers after changing model weights behind an unchanged Ollama model
tag. Migration `v14` is optional so an unapplied answer-cache table cannot make
the RAG server fail readiness; until it is applied, answer-cache calls fail open
and generation continues without persistent answer reuse.

## The scope key

`RagEngine._search_scope_key` builds one tuple covering everything that decides
what a search may return and how it ranks. Both tiers derive their keys from it,
so they cannot disagree about what counts as the same search.

Identity is included **only where the read scope actually consults it**. Read
`build_read_scope_sql`: a `public` or `shared` search binds neither agent nor
session into its SQL, an `agent` search binds only the agent, a `session` search
binds both. Keying on identity regardless would be harmless for correctness and
ruinous in practice - the MCP server mints a fresh session id per process, so
every restart would start cold against a table full of answers it is entitled to
but cannot recognize as its own.

`RagEngine.SEARCH_SCOPE_FIELDS` names every `ProjectContext` field the search SQL
may depend on. Adding a filter to `_search_uncached` without extending the scope
key is how this cache would turn into a data leak rather than a slowdown.

The key also contains the scoped `context_fingerprint`, not a whole-registry
fingerprint. It hashes the visible project roots and separately registered nested
exclusions. An unrelated project does not fragment existing entries. Adding,
moving or removing a nested root changes the parent's visible area and therefore
both its search-cache and local-answer-cache keys. File ownership is checked again
on every result, including L1/L2 hits, so older misattributed rows are omitted.
Rootless notes remain subject to project, ACL and generation partitioning. Routine
retirement stays sticky across ordinary saves; only an explicit correction or
re-indexing the exact current source can restore a retired file-backed chunk.

Explicit global search has no combined cross-project answer cache. It reuses these
independent per-project caches after resolving each current project scope, and
returns project provenance plus per-project cache details.

## Invalidation

`rag_cache_generation` holds one counter per project. Any successful knowledge
mutation bumps it, and a cached row is only served for the generation it was
computed under - so a save in one process retires every other process's cached
answers without reaching into their memory. Rows are not deleted on
invalidation: deletion races with in-flight readers and cannot reach a peer
holding a copy in RAM.

Each worker caches the counter for `RAG_CACHE_GENERATION_REFRESH_SECONDS`. That
hold is the entire staleness window of the shared cache, and it is a bound worth
stating rather than an implementation detail: a save becomes visible everywhere
within that many seconds.

### Bumping only when the corpus moved

`save()` bumped the generation once per chunk. Indexing one 35-chunk document
therefore retired every cached answer thirty-five times, and the watchdog indexer
re-indexes on every file write. Measured after three ordinary hours of editing:
generation **22**, with **16 of 16 cached rows stranded below it** — the shared
cache had a hit rate of exactly zero and would have kept it forever.

Two corrections, both of which are really the same one: bump per *change*, not
per *write*.

* `save(invalidate=False)` lets a caller take responsibility, and
  `index_document` bumps once for the whole file. One file is one change to the
  corpus, not thirty-five.
* A conflict on `dedup_key` means the content was already stored — `content_hash`
  is part of that key — so the upsert alone does not change searchable text.
  `RETURNING (xmax = 0)` distinguishes a real insert. A deliberately asserted
  `validation_status` or updated `source_snapshot` can still change evidence and
  therefore invalidates even when the text is unchanged.

Current indexing coalesces new chunks and retirement of superseded chunks into
one generation bump per logical file change. A genuinely unchanged source that
the watcher skips does not bump the counter.

Failed searches are never cached, at either tier. Every L2 operation fails open -
a cache that is down looks exactly like a cache that is cold.

### Lending the writer's connection

A writer invalidates as its last act, while it still holds a pooled connection.
Asking `ThreadedConnectionPool` for a second one there makes a writer compete
with itself: at `maxconn=16`, sixteen concurrent writers each holding one and
each wanting another exhaust the pool. `getconn()` raises, the cache path fails
open, and the failure is invisible — the write commits, the counter never moves,
and every other process keeps serving answers that write was meant to retire
until their rows expire.

This was not reasoned about in advance; it was found. A running server showed a
frozen count of twelve swallowed errors while every operation reproduced clean in
isolation, and the mechanism turned out to be exactly that — reproduced by
holding sixteen connections and calling `save()`: `PoolError: connection pool
exhausted`, `generation_bumps` stuck at zero, `save()` returning success.

So `bump_generation` takes an optional connection and every writer lends the one
it already has. `tests/unit/test_cache_connection_reuse.py` walks the engine's
AST and fails if any call site that still holds a connection does not pass it —
the guard covers writers not written yet, which is the only kind that can
reintroduce this.

The ordering is unchanged and load-bearing: the bump happens strictly **after**
the writer's commit. Bumping before it would let a peer read pre-write rows and
file them under the post-write generation, where nothing would ever retire them.

### An unreadable counter is not an unchanged one

`generation()` returns `None` when the counter cannot be read. That is not the
same as zero. A worker in that state cannot tell whether a peer has invalidated
anything, and its own remembered number still matches rows it wrote earlier — so
a lookup keyed on it would return answers a peer's write has already superseded.

Both cache tiers are therefore bypassed for that request, for reads and writes,
and the response says `{"layer": "unshared"}` rather than claiming a miss. This
is the production behavior in `RagEngine.search`: without a known generation, no
previously computed response can prove that it survived a peer's mutation.

## Configuration

| Variable | Default | Maximum | Disable with |
| --- | ---: | ---: | ---: |
| `RAG_QUERY_CACHE_TTL_SECONDS` | 45 | 3600 | `0` |
| `RAG_QUERY_CACHE_MAX_ENTRIES` | 256 | 4096 | `0` |
| `RAG_EMBEDDING_CACHE_TTL_SECONDS` | 600 | 86400 | `0` |
| `RAG_EMBEDDING_CACHE_MAX_ENTRIES` | 1024 | 16384 | `0` |
| `RAG_L2_CACHE_TTL_SECONDS` | 900 | 604800 | `0` |
| `RAG_L2_CACHE_MAX_ROWS` | 5000 | 200000 | `0` |
| `RAG_L2_CACHE_SEMANTIC_THRESHOLD` | 0.98 | 1.0 | `1.0` |
| `RAG_CACHE_GENERATION_REFRESH_SECONDS` | 5 | 300 | — |

The 0.98 value is the reusable cache implementation's default. Production
`RagEngine` overrides it to 1.0, so semantic reuse is disabled regardless of the
generic default shown here.

L2's TTL is deliberately far longer than L1's: L1 is a burst absorber measured in
seconds, L2 exists so tomorrow does not re-pay for today's answer. Correctness
does not rest on either TTL - the generation counter does - so the TTL is only a
bound on how long an unused row may sit.

## Operations

- `GET /cache/stats` — hit, miss, eviction and error counters for all tiers.
- `POST /cache/invalidate` — `{"project_id": "...", "purge": false}`. Routine
  mutations invalidate themselves; this is for what the engine cannot see, such
  as a restored dump, a manual UPDATE or a re-embed.
- Housekeeping is amortized over writes: every 64th store sweeps expired rows and
  trims the tail by least-recent use. A process that never writes never sweeps.
